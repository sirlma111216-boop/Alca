# 구조 — 엔진과 어댑터

## 한 장 요약

```
                    ┌──────────────────────────────────────────────┐
  수업 앱 ─iframe──▶│  src/embed          /embed/ 진입점            │
                    │    └ adapters/iframe/embed-host.ts           │
  수업 앱 ─npm─────▶│  src/adapters       mount / React / host     │
                    │                                               │
  교사 ───브라우저─▶│  src/standalone     참가자 입력·설정·결과      │
  학생 ───폰───────▶│    └ 실시간 화면 ──▶ src/live (WebSocket)     │
                    └───────────────────┬──────────────────────────┘
                                        │  (넷 다 같은 것을 쓴다)
                            ┌───────────▼───────────┐
                            │   src/renderer        │  Canvas·효과·입력·오디오
                            │   (엔진을 읽기만 한다) │
                            └───────────┬───────────┘
                            ┌───────────▼───────────┐
                            │   src/core            │  상태·물리·난수·점수·순위·선정
                            │   브라우저도 네트워크도 │
                            │   모른다               │
                            └───────────────────────┘
```

**게임 엔진(`src/core`)은 React·DOM·특정 배포 업체·수업 앱의 전역 상태에 의존하지 않습니다.**
브라우저 기능은 전부 어댑터에서 연결합니다. 그래서 엔진은 Node 에서 그대로 돌고,
테스트가 브라우저 없이 끝납니다.

**실시간 참여가 붙은 뒤에도 이 성질은 그대로입니다.** `src/core` 는 `WebSocket` 도
수업 코드도 모릅니다. 네트워크는 `src/live` 한 층에만 있고, `core` 는 여전히
`computeRanking` · `selectPresenters` 같은 **순수 함수**로만 불립니다
(그 호출은 서버가 아니라 **교사 화면**에서 일어납니다).

## 폴더와 책임

| 폴더 | 책임 | 의존 |
|---|---|---|
| `src/core` | 게임 상태, 물리, 난수, 점수, 순위, 선정 | **없음** (표준 JS 만) |
| `src/renderer` | Canvas 렌더링, 효과, 입력, 오디오 | `core` (읽기 전용) |
| `src/adapters` | React 컴포넌트, 일반 JS 임베드 API, iframe 통신 | `core`, `renderer` |
| `src/live` | **실시간 참여 — 브라우저 쪽.** WebSocket 연결·재접속·기기 토큰·수업 코드 기억 | `core` (타입만), `worker/protocol` (타입만) |
| `src/standalone` | 참가자 입력, 설정, 경기·결과 화면, **실시간 교사·학생 화면** | `core`, `adapters`, `live` |
| `src/embed` | `/embed/` 페이지 진입 스크립트 | `adapters` |
| `worker/` | **실시간 참여 — 서버 쪽.** Cloudflare Worker + Durable Object | 없음 (Cloudflare 런타임만) |
| `examples` | 일반 HTML 호스트, React 호스트 예제 | 배포된 게임 / npm 패키지 |

### `worker/` 안

| 파일 | 하는 일 |
|---|---|
| `protocol.ts` | 메시지 봉투, 수업 코드 만들기·다듬기, 닉네임 거르기, `RosterView`/`MatchStartView` 등 **양쪽이 공유하는 타입** |
| `room-do.ts` | `RoomSession` — 수업 하나 = Durable Object 하나. 명단·시작 신호·점수 모으기 |
| `index.ts` | 진입점. `/ws` 와 `/api/*` 만 처리한다 |

`worker/` 는 `src/` 를 import 하지 않습니다. 반대로 `src/live` 는 `worker/protocol` 의
**타입만** 가져옵니다(`import type`). 한쪽 코드가 다른 쪽 번들에 섞이지 않게 하려는 것입니다.
타입 검사는 `tsconfig.worker.json` 으로 따로 돌립니다(`npm run typecheck` 가 둘 다 돌립니다).

### 의존 방향은 한 방향

```
core ← renderer ← adapters ← standalone / embed
  ↑                              │
  └── live ←────────────────────┘        live 는 core 의 타입만 본다
       │
       └─(WebSocket)─▶ worker/   서버는 src/ 를 전혀 모른다
```

거꾸로 가는 import 가 하나라도 생기면 엔진이 브라우저에 묶여 버립니다.
`core` 안에서 `document`·`window`·`AudioContext`·`React`·**`WebSocket`·`fetch`** 를 쓰지 마세요.

**`core` 는 여전히 네트워크를 모릅니다.** 실시간 모드에서도 `core` 가 하는 일은
단독 실행과 똑같습니다 — 판을 만들고, 물리를 돌리고, 순수 함수로 순위를 냅니다.
"누가 접속했는지", "점수를 어디로 올리는지" 는 `core` 바깥의 이야기입니다.
그래서 실시간 기능을 통째로 들어내도 `core` 의 테스트는 한 줄도 바뀌지 않습니다.

## 실시간 참여 — 왜 폰에서 계산하는가

실시간 모드에서 **패들 입력을 서버로 왕복시키지 않습니다.** 대신 학생 폰이 각자
**같은 `seed` 로 같은 판을** 로컬에서 돌리고, 서버는 점수만 모읍니다.

```
  교사 화면 ──WebSocket──▶ Durable Object (수업 코드 1개 = 방 1개) ◀──WebSocket── 학생 폰
   │                          명단·시작 신호·점수 모으기만 한다                    │
   │                                                                              │
   └─ core 의 순수 함수로 최종 순위·발표자를 낸다        각자 core 로 판을 돌린다 ─┘
```

입력을 서버로 보내면 왕복 지연(학교 와이파이에서 0.05~0.3초)만큼 패들이 늦게 움직입니다.
30초짜리 벽돌깨기에서는 "받았는데 안 받아졌다" 가 계속 일어나 게임이 성립하지 않습니다.
공정성은 지연을 없애는 쪽이 아니라 **같은 판을 주는 쪽**으로 확보했습니다 —
엔진이 이미 결정적(`seed` 하나로 벽돌·아이템·서브 각도가 전부 결정)이고,
물리가 고정 스텝이라 **기기 성능이 결과를 바꾸지 못하기** 때문에 가능한 선택입니다.

그 대가로 **점수는 서버가 검증한 값이 아닙니다.** 이 게임의 용도(발표자 선정)에는
충분하다고 판단했고, 그 판단의 근거와 한계는 [protocol.md](protocol.md) 9절에 적어 두었습니다.

메시지 형식·권한·묶어 보내기는 [protocol.md](protocol.md) 8절,
교사가 읽을 사용법은 [live-mode.md](live-mode.md) 입니다.

| `items.ts` | 아이템 효과 상태 기계 (지속·중첩·교체 규칙) |
| `engine.ts` | `Arena` — 한 참가자의 경기장 시뮬레이션 |
| `autopilot.ts` | 자동 경기용 패들 조종기 |
| `scoring.ts` | 순수 함수 — 점수 계산 |
| `ranking.ts` | 순수 함수 — `rank` + `eligibleRank` + 동점 정보 |
| `selection.ts` | 순수 함수 — 발표자 선택과 선정 이유 |
| `events.ts` | 재현용 입력 기록/재생 |
| `match.ts` | `Match` — 여러 경기장과 시계를 총괄 |

### 고정 시간 간격

물리는 **1/120초 고정 스텝**으로만 전진합니다. 렌더링과 분리돼 있습니다.

```ts
// 어댑터의 구동 루프 (요지)
acc += Math.min(now - last, 250)
let steps = 0
while (acc >= STEP_MS && steps < MAX_STEPS_PER_FRAME) {
  match.step(input.take())
  acc -= STEP_MS
  steps += 1
}
renderer.render(acc / STEP_MS)   // 남은 비율로 보간해 부드럽게
```

- 경기 시계는 벽시계가 아니라 **진행한 스텝 수**입니다. 30초 = 정확히 3,600 스텝.
- 프레임이 밀리면 **실시간만 길어지고** 결과는 완전히 동일합니다.
- 한 프레임에 최대 16스텝까지 따라잡습니다. 더 밀리면 경기가 실시간 기준으로
  천천히 흐르지만 스텝을 **건너뛰지 않으므로** 순위가 달라지지 않습니다.
- 탭이 숨으면 공·아이템 낙하·효과 지속 시간·제한 시간이 **함께** 멈춥니다.
  돌아와도 자동 재개하지 않고 사용자가 누를 때까지 기다립니다.

### 해상도 독립 좌표계

경기장은 항상 **320 × 440 논리 단위**입니다. 렌더러가 배율만 조정하므로
창 크기나 기기 픽셀 비율이 바뀌어도 **물리적 난이도가 달라지지 않습니다.**

### 결정성

같은 `seed` + 같은 설정 + (직접 조작이면) 같은 입력이면 항상 같은 결과가 나옵니다.

- `core` 안에서 `Math.random()` 과 `Date.now()` 를 쓰지 않습니다.
  난수는 `createRng(seed)`, 시각은 `Match` 에 주입되는 `now()` 만 씁니다.
- 참가자 스트림 seed = `해시(매치 seed) XOR 해시(참가자 ID)`.
  XOR 이므로 **입력 순서·화면 위치와 무관**합니다.
- 아이템 배치는 **매치 seed 만** 씁니다 → 전원 동일한 판.
- `resultId` 생성에만 주입된 `random()` 을 쓰며, 시뮬레이션에는 관여하지 않습니다.

### 충돌 처리

- 공의 이동 경로 **전체**를 쓸어 검사합니다 → 빠른 공도 벽돌을 관통하지 않습니다.
- 모서리 동시 충돌은 두 축을 함께 반사하고, 벽돌은 **한 번만** 셉니다.
- 패들 안에 끼이면 가장 얕은 면으로 밀어냅니다.
- 패들에 맞은 위치에 따라 반사각이 달라지되(최대 70°), 수직 성분의 하한을 지켜
  **수평으로 영원히 왕복하지 않습니다.**
- 공과 레이저 탄환이 같은 스텝에 같은 벽돌을 맞혀도 점수와 캡슐은 한 번만 발생합니다
  (먼저 처리된 쪽에서 `alive = false` 가 되고, 캡슐은 벽돌마다 `itemSpawned` 로 잠깁니다).

### 이벤트가 두 갈래로 나간다

경기 중 일어난 일(`ArenaEvent`)은 두 곳이 각각 받습니다.

- `arena.drainEvents()` — **렌더러**가 파티클·소리·점수 팝업에 씁니다(꺼내 가면 사라짐).
- `arena.eventSink` — **재현 로그 수집기**가 씁니다(`collectArenaEvents: true` 일 때만).

둘이 독립적이라 서로의 이벤트를 빼앗지 않습니다. 이벤트는 시뮬레이션에 영향을 주지 않으므로
아무도 소비하지 않아도 결과가 달라지지 않습니다(버퍼는 512개에서 오래된 것부터 버립니다).

### Match 와 Arena

- **자동 경기** — `Match.step()` 이 모든 `Arena` 를 **같은 스텝으로** 전진시킵니다.
  화면에 보이지 않는 참가자도 똑같이 계산합니다. 축약하는 것은 **렌더링뿐**입니다.
- **직접 조작** — 현재 참가자의 `Arena` 하나만 전진시킵니다.
  모든 참가자가 같은 `seed` 로 만들어지므로 **판·아이템·서브 각도가 전부 같습니다.**

측정치: 40명 × 30초 자동 경기 전체 시뮬레이션이 약 100ms (실시간 대비 약 290배 여유).

## src/renderer — 그리기·소리·입력

엔진 상태를 **읽기만** 합니다. 절대 바꾸지 않습니다.

| 파일 | 하는 일 |
|---|---|
| `types.ts` | 렌더러·오디오·입력의 공개 인터페이스 |
| `palette.ts` | 색과 글꼴 — 캔버스와 CSS 가 같은 값을 쓰도록 한곳에 모음 |
| `canvas.ts` | `createMatchRenderer` — **캔버스 하나**에 모든 경기장을 격자로 그림 |
| `particles.ts` | 고정 크기 풀을 재사용하는 파티클 |
| `audio.ts` | `createGameAudio` — WebAudio 합성. **음원 파일 없음** |
| `input.ts` | `createInputController` — 마우스·키보드·터치 |

### 캔버스 하나

참가자가 40명이어도 캔버스는 하나입니다. 참가자마다 캔버스를 만들면
합성 비용과 메모리가 감당이 안 됩니다.

- `full` (확대/1인) — 벽돌 입체감, 아이템 문양, 내구도 금, 공 잔상, 캡슐 아이콘,
  레이저 탄환, 바닥 보호막, 패들 무기 상태, 활성 효과와 남은 시간.
- `mini` (여러 명) — 단색 벽돌, 점 공, 파티클 없음, 효과는 작은 아이콘 줄로 요약.
  닉네임과 점수는 **항상** 읽히게 그립니다.

배경·벽·격자는 오프스크린 캔버스에 한 번 그려 재사용합니다.

### 입력 격리

키보드 리스너는 `window` 가 아니라 **게임 컨테이너 요소**에 붙습니다.
한 페이지에 게임이 여러 개 떠 있어도 서로의 입력을 가로채지 않습니다.
`Space` 의 기본 동작(페이지 스크롤)은 게임에 초점이 있을 때만 막습니다.

모바일에서는 패들 드래그와 발사 버튼이 **다른 `pointerId`** 로 관리되어 서로 방해하지 않습니다.

### 오디오

`AudioContext` 는 만들어만 두고 **사용자의 첫 조작 때 `unlock()`** 에서 깨웁니다.
음소거 상태는 브라우저 로컬 저장소에 기억합니다.
같은 종류의 소리는 30ms 안에 한 번만 나고, 동시 발음 수에 상한이 있어
40명 경기에서 소리가 폭발하지 않습니다.

## src/adapters — 바깥과 이어지는 곳

| 파일 | 하는 일 |
|---|---|
| `types.ts` | `BrickPickOptions`, `BrickPickController` — 외부에 보이는 표면 전부 |
| `mount.ts` | `mountBrickPick(container, options)` — **게임 화면 + 구동 루프** |
| `react.tsx` | `<BrickPick />` — 같은 옵션을 받는 React 껍데기 |
| `index.ts` | 기본 진입점. **React 를 import 하지 않는다** |
| `iframe/protocol.ts` | 메시지 타입·검증·origin 허용 목록 (양쪽이 공유) |
| `iframe/embed-host.ts` | iframe **안쪽**(게임 쪽) 처리 |
| `iframe/host-client.ts` | **부모**(수업 앱) 쪽 도우미 |

`mountBrickPick` 은 "게임 화면"만 만듭니다. 참가자 입력·설정 화면은 들어 있지 않습니다
(그건 단독 실행 앱의 몫). 그래서 임베드·React 컴포넌트·단독 실행이 **같은 것**을 씁니다.

### React 를 프레임마다 다시 그리지 않는다

경기 화면의 HUD 는 React 가 아니라 **DOM 을 직접**, 그것도 5Hz 정도로만 갱신합니다.
바뀐 텍스트만 바꿉니다. 프레임마다 React 상태를 올리면 40명 경기에서
렌더 트리 전체가 초당 60번 다시 그려집니다.

### 진입점이 두 개인 이유

`package.json` 의 `exports` 가 세 갈래입니다.

```
brickpick          → dist-lib/brickpick.js        (React 없음)
brickpick/react    → dist-lib/brickpick-react.js  (React 필요)
brickpick/host     → dist-lib/brickpick-host.js   (iframe 호스트 도우미)
brickpick/style.css
```

React 를 안 쓰는 수업 앱이 React 를 끌어오지 않게 하기 위해서입니다.
`react` / `react-dom` 은 **선택적 peerDependency** 입니다.

### 정리(cleanup)

`controller.destroy()` 는 `requestAnimationFrame` 취소, 모든 리스너 제거,
렌더러·오디오·입력 정리, `match.destroy()`, 컨테이너 비우기를 **전부** 합니다.
여러 번 불러도 안전하고, 반복해서 열고 닫아도 타이머·리스너가 누적되지 않습니다.

## 빌드가 둘로 나뉜 이유

| | 설정 | 출력 | 용도 |
|---|---|---|---|
| 앱 | `vite.config.ts` | `dist/` | 정적 사이트. `/` 와 `/embed/` 두 진입점 |
| 라이브러리 | `vite.lib.config.ts` + `tsconfig.lib.json` | `dist-lib/` | npm 패키지 (ESM + `.d.ts`) |
| 실시간 서버 | `wrangler.jsonc` + `tsconfig.worker.json` | (없음 — wrangler 가 직접 올린다) | `/ws`, `/api/*` |

출력이 섞이면 배포에 소스맵과 타입 선언이 올라가거나, 패키지에 HTML 이 섞입니다.
`npm run build` 는 앞의 둘을 돕니다.

`worker/` 는 **vite 를 거치지 않습니다.** `wrangler deploy` 가 `main: "worker/index.ts"` 를
직접 번들해 올립니다. 그래서 npm 패키지(`dist-lib/`)에는 실시간 코드가 한 줄도 들어가지
않습니다 — npm 으로 쓰는 수업 앱에는 서버가 필요 없기 때문입니다.

SPA 라우터를 쓰지 않습니다. 진입점이 `/` 와 `/embed/` 두 개뿐인 **멀티페이지 정적 사이트**라
어떤 호스팅에서도 직접 접근·새로고침이 그냥 동작하고, rewrite 규칙이 필요 없습니다.

## 의도적으로 하지 않은 것

- **같은 경기장을 여러 명이 함께 하는 멀티플레이** — 없습니다. 실시간 참여는
  **각자 같은 판을 따로** 하는 방식입니다. 남의 공이 내 화면에 들어오지 않습니다.
  공을 주고받으려면 상태 동기화·지연 보정·권위 서버가 필요한데, 30초짜리 수업용 추첨에
  그만한 구조를 들이지 않았습니다.
- **계정·데이터베이스** — 없습니다. 실시간 서버가 생겼지만 로그인도 DB 도 없습니다.
  **수업 코드 6자리가 가장 가벼운 계정**이고, 방 상태는 Durable Object 안에 8일만 있습니다.
- **서버 측 성적 검증** — 점수는 클라이언트에서 계산됩니다. 실시간 모드에서도 같습니다.
  수업용 선정에 맞게 설계했고, 불필요한 인증 시스템을 넣지 않았습니다.
  ([protocol.md](protocol.md) 9절)
- **모든 요청을 Worker 로 보내기** — `run_worker_first` 를 `true` 로 두지 않고
  `["/ws", "/api/*"]` 목록으로 두었습니다. 게임 화면·JS·CSS 는 예전처럼 Cloudflare 가
  바로 내려줍니다. ([deployment.md](deployment.md) 2-E)
- **외부 글꼴·음원 파일** — 전부 시스템 글꼴과 코드 합성입니다. 네트워크 요청이 없습니다.
